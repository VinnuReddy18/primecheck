## The pipeline proved the chain on its own

The pod the pipeline deployed into its own throwaway cluster was asked which commit it came from:

```
{"version":"0.1.0","git_sha":"52ca5359b39b4da768d64ad60a49eed7b6fa773c","build_time":"2026-10-18T08:16:12Z"}
{"n":999983,"prime":true,"elapsed_ms":0.008}
{"n":999984,"prime":false,"elapsed_ms":0.011}
```

The commit became a build argument, the argument became an image, the image became a running pod,
and the pod named the commit back. No human in the loop, and the job fails if those disagree.

The same job then deployed a deliberately broken image tag:

```
Error: UPGRADE FAILED: context deadline exceeded
the bad release failed to become ready, as expected
Rollback was a success! Happy Helming!
deployment "primecheck" successfully rolled out
```

The rollout refused to finish rather than replacing healthy pods with broken ones.

## The user journey on the local cluster

Through the ingress, not a port forward:

```
/version         {"version":"0.1.0","git_sha":"52ca535","build_time":"2026-10-18T08:17:00Z"}
/readyz          {"status":"ready","sieve":"warm","primes":78498}
/check?n=999983  {"n":999983,"prime":true,"elapsed_ms":1.075}
/check?n=999984  {"n":999984,"prime":false,"elapsed_ms":0.636}
/check?n=-1      HTTP 400  {"detail":"n must not be negative"}
/admin/flags     HTTP 401  {"detail":"invalid admin token"}
x-request-id     e82bfad8e8bbda51fd8f878eae65dc7b
```

999983 is prime and 999984 is not, so the answers are correct and not merely present. Bad input is
rejected, the admin surface refuses an unauthenticated caller, and the request id in the response
header is the same id that appears on the JSON log lines for that request.

## Fault and recovery

**Symptom.** A config change raising `SIEVE_LIMIT` to 400000000 was released. The rollout never
completed.

**Hypothesis.** The sieve allocates about a byte per candidate, so that asks for roughly 400 MB
inside a 256 MiB container. The new pods should be dying on memory before they can warm.

**Evidence.** The replacement pod reported `exitCode 137`, `reason OOMKilled`, four restarts and a
startup probe refusing connections, while the Service endpoints still listed the two original pod
IPs. Confirmed, and the old replicas were still serving.

**Change.** `helm rollback primecheck`.

**Verification.** Both original pods ready, `/version` still reporting `52ca535`, the sieve warm at
78498 primes, `/check?n=999983` correct, and `SIEVE_LIMIT` back to 1000000. The rollback restored
configuration as well as workload.

**Did users see it.** A probe called `/check` twice a second for the whole drill:

```
probe requests sent:      143
answered 200:             143
anything else:            0
```

Zero failed requests. That is `maxUnavailable: 0` plus a readiness probe that tells the truth: a
replacement has to prove itself before a serving pod is removed. The bad config reached the cluster
and never reached a user.

## What this does not show

The deploy to the long lived cluster is an operator run script after the approval gate, not a job
inside the pipeline, because the cluster is local and hosted runners have no route to it. CI
compensates by deploying into a cluster of its own and verifying there, so the chart and the image
are proven, but the final `helm upgrade` against this cluster is run by hand.

Ingress TLS uses the controller's self signed certificate, so the captures use `http`. There is no
log aggregation, so log evidence is `kubectl logs` rather than a query over a retained store. Jaeger
keeps traces in memory, so the trace above will not survive a Jaeger restart. The load behind these
numbers is a short shell loop, so the latency figures are honest for an idle local cluster and are
not capacity numbers.
